# Serving RUM packages

`/.rum/@adobe/helix-rum-js@<spec>/<file>` and `/.rum/@adobe/helix-rum-enhancer@<spec>/<file>` are served **only** from the packages' release branches on aem.live, and **only** when the file's decoded bytes match an approved SHA-384 digest. There is no fallback to jsDelivr, unpkg or any other CDN: a file that can't be verified is not served.

## Resolution

1. `<spec>` maps to a branch as before: `2.17.0` → `release-2-17-0`, `~2.17` → `release-2-17-x`, `^2` → `release-2-x`.
2. An alias is resolved to the exact version it points to, from its `release-manifest.json` or, for older releases, its `package.json`.
3. The file is fetched from that version's **write-once** `release-X-Y-Z` branch. Repository rulesets block updates and deletion of these branches for everyone, so the bytes of a published version can't change.
4. The approved digest comes from that branch's `release-manifest.json` (releases since rum-js 2.18.0 / rum-enhancer 2.53.0). Older releases have no manifest; their digests come from `src/legacy-releases.mjs`.
5. Missing, unlisted or mismatched files get a 404/502 with `x-error` and `Cache-Control: no-store`, and a `rum-package-refused` log line.

Successful responses carry `x-rum-release` (the exact version) and `x-rum-integrity` (the verified digest). Bodies are served decoded; the CDN compresses them.

`/.rum/web-vitals/dist/web-vitals.iife.js`, which enhancer releases before the bundled CWV plugin load at runtime, is served from `src/vendor/web-vitals.iife.js` of `helix-rum-enhancer@^2`, the pinned copy each enhancer release ships and lists in its manifest. Every other `/.rum/web-vitals` path is a 404.

## Legacy releases

`src/legacy-releases.mjs` is generated by `node tools/legacy-releases.mjs` from the npm tarballs, each checked against the registry's sha512 integrity. It covers only releases without a manifest that still get traffic (rum.hlx.page logs, November 2026), including what the `^1` and `^2` aliases point to. To add a version, add it to `VERSIONS` in the tool, rerun it and review the diff. Its release branch must also contain the file; use the libraries' **Backfill release branch from npm** workflow if it doesn't.

## Pre-deploy guard

Because nothing falls back, the release job runs `npm run verify-package-coverage` before `semantic-release` deploys. `tools/verify-package-coverage.mjs` replays every package request that carries real traffic through this handler, against the live release branches, on all three backends (aem.live, aem-fastly.live, aem-cloudflare.live):

- the alias requests in `ALIAS_REQUESTS` (`^2` and `^1` for both packages, including every enhancer plugin and the vendored web-vitals source);
- every approved file of every release in `src/legacy-releases.mjs`, at its exact version.

If any of them would not be served verified, the deploy stops and the failing URLs are listed. Before the first deploy this requires rum-enhancer 2.53.0 (vendored web-vitals and all plugins on `release-2-x`) and the backfills, including the exact `release-1-9-0` / `release-1-23-1` branches that `^1` resolves to. Run it locally any time with `npm run verify-package-coverage`.

The same check also runs **every 3 hours** (`.github/workflows/package-coverage.yml`) once releases are enabled. A library release can move an alias such as `release-2-x` to a version that no longer serves a file older loaders still request (a removed plugin, or the vendored web-vitals); the collector deploy wouldn't notice. A failing scheduled run opens an issue titled "Served RUM package files would fail verification" with the refused URLs. While it is open, a run comments only when the set of refused URLs changes (`tools/package-coverage-issue.mjs` marks each report). It also reports a run where the guard never produced results, for example because `npm ci` failed. When a library drops a file that loaders still request, keep it in the release (or add a redirect in the collector) before releasing.
